# Reduce Communication Hub polling and widen the phase-11 migration gate

This change reduces Communication Hub polling from 15 seconds to 60 seconds, avoids loading notification preferences on routine refreshes, and adds a guard against overlapping summary/detail refreshes. It also changes the phase-11 workflow confirmation from `APPLY_35_THEN_36` to `APPLY_FULL_35_THROUGH_40` and wraps the read-only preflight in output parsing before allowing apply. The communication request/authentication paths and the Supabase Storage download path are otherwise unchanged. **Watch for:** **confirmed/high** preflight failures can be classified as clean; **confirmed/high** full migration approval can leave the checked-in V1 worker incompatible with migration 40; **confirmed/medium** the refresh guard drops a view-change or preference-recovery refresh while another refresh is active.

**Verdict**: NEEDS_CHANGES
**Recommendation**: CHANGES_REQUIRED

## High-level view

Communication refreshes now fetch preferences only on the initial/view-effect load or an explicit preference-recovery attempt, while polling, focus, visibility, and manual refreshes continue to update threads and notifications without that endpoint. The 60-second cadence is implemented, but **confirmed/medium** the new boolean guard coalesces by dropping requests rather than replaying the latest intent.

The migration workflow now requires and recognizes an explicit full 35–40 confirmation. Its shell preflight converts the gate’s exit status into text and allows apply based on a six-code grep, creating a **confirmed/high** fail-open path for other gate failures; the pure gate tests do not exercise this shell contract.

No API route, session request helper, RLS policy, attachment authorization, Storage bucket, worker source, or n8n workflow is modified by this diff. The broadened migration authorization still reaches migration 40, which sets the database worker contract to V2 while the checked-in worker reports V1; this is a **confirmed/high** paired worker rollout/readiness gap.

1. **Preflight failure is treated as clean** — **confirmed/high**: the wrapper suppresses `--inspect` failures and only recognizes six ledger violation codes. Preserve a nonzero inspection exit as a hard stop or consume a machine-readable result that distinguishes clean, violation, and execution failure before enabling apply.
2. **Migration 40 can strand the production worker** — **confirmed/high**: the newly accepted full 35–40 confirmation includes migration 40, which requires `AUTOMATION_WORKER_V2`, while the checked-in worker advertises `AUTOMATION_WORKER_V1`. Keep the gate scoped to the compatible subset or require a paired V2 worker release/readiness check before applying 40.
3. **View changes can publish stale thread data** — **confirmed/medium**: switching views resets state and starts a new refresh, but the in-flight guard drops that refresh; the old request can then write its prior view’s results into the cleared Sent/Inbox state. Queue or invalidate refresh generations so the current view always gets a request and stale responses cannot commit.
4. **Preference recovery can remain optimistic** — **confirmed/medium**: if a preference PUT fails while another refresh is active, the recovery call returns immediately and the optimistic checkbox state is not reconciled from the server. Queue the recovery or make the failure path retry after the active refresh completes.
5. **The changed shell contract is untested** — **confirmed/low**: the new workflow parses process output, but the added tests never run that wrapper or inject an unrecognized gate failure. Add a shell-level test or replace parsing with a structured gate result whose failure status is asserted.

### Refresh cadence, conditional preferences, and recovery

`POLL_INTERVAL_MS` is now 60,000 ms. The interval, window-focus listener, and visibility listener still call the same visible-only refresh function, and their cleanup remains tied to the `refresh` callback. Routine refreshes call `loadSummary` without `/api/communications/preferences`; the initial effect passes `includePreferences=true`, and the preference PUT failure path requests a preference reload. The existing selected-thread `mergeLatest` update combines incoming messages with the current message set, so the polling change does not discard older pages during a normal latest-detail refresh.

The new guard at `CommunicationWorkspace.tsx:78-91` is not a queue: every call while `refreshInFlightRef.current` is true returns without recording that a refresh is needed. This affects manual Refresh, focus, visibility, polling, and the explicit preference-recovery call. It also interacts with the view effect: `CommunicationWorkspace.tsx:95-99` clears `summaryViewRef`, selection, threads, and detail, then the new view’s effect calls `refresh(true, true)`. If the prior view’s request is still pending, that call is dropped; when the old `loadSummary` resolves it uses its closed-over `view` and writes the old list into the newly cleared state. This is a **confirmed/medium** stale-view race, not a speculative React dependency issue.

The missing behavior is generation/intent handling, not an omitted dependency or listener leak. Existing tests cover visibility suppression and focus refresh, but `CommunicationWorkspace.test.tsx:229-243` advances only 15.1 seconds while hidden; **confirmed/low** coverage is missing for a visible 60-second tick, queued refreshes during an in-flight request, stale-result rejection on view switches, and preference recovery after a guard collision.

### Full phase-11 confirmation and worker compatibility boundary

The dispatch validation now accepts `apply:APPLY_FULL_35_THROUGH_40` (`.github/workflows/09-phase11-production-migration-dispatch.yml:141-144`), and the gate’s apply step is enabled after the new preflight (`.github/workflows/09-phase11-production-migration-gate.yml:178-185`). The checked-in migration runner already pins 35, 36, 38, 39, and 40, so this diff adds no migration SQL and does not itself change Storage, n8n, or worker source code. It does, however, change the operator-facing authorization from the old 35/36 confirmation to an explicit full-boundary confirmation.

Migration `20260810000040_harden_automation_worker_claim_drain.sql` changes `automation_execution_contract.worker_version` to `AUTOMATION_WORKER_V2`. The checked-in `apps/api/src/modules/automation/automation.execution.validation.js` exports `AUTOMATION_WORKER_V1`, and `createWorker().start()` performs the compatibility check before becoming ready. The production worker is deployed separately by `.github/workflows/08-deploy-aca-production.yml`; this PR does not pair that release or add a readiness gate. Applying the newly authorized full boundary can therefore make the current worker fail readiness or stop processing until a compatible worker artifact is deployed. This is a **confirmed/high** rollout compatibility gap. The action is to retain the compatible migration scope or make migration 40 contingent on the exact paired V2 worker SHA and successful readiness evidence.

### Production preflight fail-closed behavior

The preflight changed from directly running the gate to capturing all output while forcing the command’s exit status to success (`.github/workflows/09-phase11-production-migration-gate.yml:162-175`). It then searches only for `ORDERING_INVALID`, `LEDGER_CHECKSUM_MISMATCH`, `UNEXPECTED_POST_31_MIGRATION`, `PREDECESSOR_MISSING`, `STAGING_ONLY_37_PRESENT`, and `LEDGER_INVALID`. The underlying script can instead fail with target verification, source-hash, transaction-boundary, database, or other gate errors. Those errors contain no listed violation token, so the wrapper writes `violations_detected=false`; an apply is then eligible even though the mandatory read-only preflight did not complete successfully. The apply invocation will often fail again, but a transient preflight failure is not allowed to authorize a later mutation attempt. This is a **confirmed/high** fail-open control-path bug. The preflight must fail on the command status and only treat an explicitly successful, violation-free inspection as clean; a structured output file/result would avoid brittle stderr parsing.

The added migration tests pass and cover clean/pending ledgers, ordering, checksum mismatch, migration 37, no-op apply, and inspect mutation behavior. They call `runPhase11ProductionMigrationGate` or `evaluateProductionLedger` directly; none executes the GitHub Actions shell wrapper, injects an unrecognized gate error, or verifies that an inspection failure prevents the apply step. This is a **confirmed/low** coverage gap supporting the preflight finding.

### API/authentication and secondary-system boundary

The communication component still receives `request` from the owner or portal session boundary. Those helpers continue to attach bearer tokens, refresh on 401, and send credentials; the API communication router still applies its auth middleware and the service resolves the actor/owner participant scope before preferences, notifications, thread, and attachment operations. Attachment downloads still go through the authenticated API endpoint and return a signed URL. No changed line broadens API authorization, bypasses RLS, writes portal data to browser storage, changes the private communication bucket, or changes n8n/webhook wiring. Those surfaces are therefore unaffected by this PR based on the checked-in diff.

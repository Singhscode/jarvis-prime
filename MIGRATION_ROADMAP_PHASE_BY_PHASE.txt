  [ ] Engine secrets stored in cloud secret manager
  [ ] CI/CD pulls secrets at deploy time
  [ ] Team documented on how to add/rotate secrets

  ✅ Rotation possible without code changes
  ✅ .env used only for local development

Status: 🔵 PLANNED

Objective:
  Encrypt sensitive database fields (tokens, cookies, keys)
  - ✅ Transparent encryption at field level
  - ✅ Master key in a managed KMS / secret store (not in database)
  - ✅ Support for per-tenant key rotation
  - ✅ Backward compatible with existing data

Implementation:

     - user_tokens (Gmail, Salesforce, etc.)

     - api_keys (stored for user's integrations)
     - email_signatures (PII)
  4. Create migration to encrypt existing data
  5. Add encryption/decryption wrappers to ORM
  6. Implement key rotation procedures

Database Schema Changes:
  ALTER TABLE users ADD COLUMN tokens_encrypted BYTEA;
  ALTER TABLE integrations ADD COLUMN oauth_encrypted BYTEA;

Secret Store Integration:
  - Master key: jarvis-prime/{env}/db-master-key
  - Key rotation: quarterly
  - Key versioning: support multiple keys during rotation

Success Criteria:
  ✅ All sensitive DB fields encrypted
  ✅ Zero performance degradation
  ✅ Transparent encryption (no application changes)
  ✅ Key rotation without downtime

PHASE 1C: IDENTITY & RLS MULTI-TENANCY (Keycloak/Auth0 + Postgres RLS)
──────────────────────────────────────────────────────────────────────
Priority: 🔴 P0 (CRITICAL — Enables multi-tenant support)
Timeline: Days 14-21
Status: 🔵 PLANNED

Objective:
  Complete tenant isolation via identity provider + database RLS
  - ✅ Multiple clients on shared infrastructure
  - ✅ Database enforces tenant access (RLS policies)
  - ✅ SSO support (Okta, Google Workspace, etc.)
  - ✅ Per-tenant admin roles

Architecture:
  ┌─ User Logs In ──→ Keycloak/Auth0 ──→ JWT Token ──┐
  │                                                    ▼
  │  Application Layer                     JWT includes: tenant_id
  │  - Validate JWT                                    sub (user)
  │  - Extract tenant_id from JWT                      roles (admin, etc.)
  │  - Set app_context.current_tenant_id              
  │                                                    ▼
  │  Database Layer                        SET app.current_tenant_id
  │  - RLS policies check tenant            ↓
  │  - All queries filtered by tenant     Supabase RLS enforces:
  │                                         SELECT * FROM prospects
  │                                         WHERE tenant_id = current_tenant_id
  └───────────────────────────────────────────────────────────┘

Implementation:
  1. Set up Keycloak (Docker) or Auth0 account
  2. Configure client credentials flow for background jobs
  3. Add JWT validation middleware
  4. Extract tenant_id from JWT, set app context
  5. Create RLS policies for all tables:
     - prospects: CREATE POLICY tenant_isolation ON prospects
     - campaigns: CREATE POLICY tenant_isolation ON campaigns
     - events: CREATE POLICY tenant_isolation ON events
     - messages: CREATE POLICY tenant_isolation ON messages
  6. Create admin roles (super_admin, tenant_admin, user)
  7. Implement audit tables (who accessed what, when)

RLS Example Policy:
  CREATE POLICY tenant_isolation ON prospects AS PERMISSIVE
    FOR SELECT TO authenticated
    USING (tenant_id = (auth.jwt() ->> 'tenant_id')::uuid)

Success Criteria:
  ✅ User can only access their tenant's data
  ✅ Database enforces isolation (no app bugs can leak data)
  ✅ SSO login working (Google, Azure, Okta)
  ✅ Admin portal shows only their tenant's prospects/campaigns
  ✅ Background jobs use service account (no JWT required)

─────────────────────────────────────────────
Priority: 🟡 P1 (Core reliability)
Timeline: Days 21-28
Status: 🔵 PLANNED

Current State:
  - Cron-based checks (fragile, no recovery)
  - In-memory retry logic
  - No state persistence
  - Hard to debug

Target State:
  - Temporal workflows (AWS MWAA, Temporal Cloud, or self-hosted)
  - State machines with full history
  - Automatic retry + human intervention on failures
  - Audit trail of all workflow executions

Workflows to Migrate:
  1. Daily Outreach Pipeline
     source → score → send emails → log events
  
  2. Reply Processing
     receive email → classify → trigger action → update DB
  
  3. Campaign Analytics
     collect metrics → calculate KPIs → alert team
  
  4. LinkedIn Automation
     daily connect limit → message queue → send

Implementation:
  1. Deploy Temporal Cloud or self-hosted Temporal
  2. Define workflow functions (step 1-4 above)
  3. Implement activities (actual business logic)
  4. Set up worker processes
  5. Create workflow triggers (scheduled, webhook, manual)
  6. Implement dashboard to monitor workflow executions

Benefits:
  ✅ No lost work if process crashes (retry from last checkpoint)
  ✅ Full audit trail of all runs
  ✅ Easy to add error handling (human approval workflows)
  ✅ Scales to thousands of tenants

     - Extract key information
     - Suggest follow-up action

     - Recommend subject line changes
     - Suggest best send times per recipient

Implementation:
  1. Add pgvector to Supabase
  2. Create vector embeddings for:
     - Past emails (context)
     - Prospect profiles (enrichment)
     - Customer feedback (improvements)
  3. Implement LangGraph state machines
  4. Create agent orchestrator (choose right agent for task)
  5. Implement memory store (Supabase + Redis for speed)

Example LangGraph Workflow:
  state = {
    "email_to_send": None,
    "recipient": {...},
    "context": [],  # Similar past emails
    "draft": None,
    "feedback": None,
    "approved": False
  }
  
  email_agent.draft_email(state)
    → retrieve_context(state)
    → generate_draft(state)
    → state["draft"] = email
  
  human_feedback(state)
    → state["feedback"] = approval
  
  if state["approved"]:
    → send_email(state)

Success Criteria:
  ✅ AI agents write emails with 90%+ approval rate
  ✅ Reply classification accuracy >95%
  ✅ Vector search finds relevant past emails <100ms
  ✅ Agents learn from feedback (improve over time)

PHASE 3A: CACHING & DISTRIBUTED RATE LIMITING (Redis)
──────────────────────────────────────────────────────
Priority: 🔵 P2 (Scale & optimization)
Timeline: Days 42-49
Status: 🔵 PLANNED

Current State:
  - In-memory rate limiting (only works on 1 instance)
  - No distributed cache
  - Secrets cached locally per instance

Target State:
  - Redis for:
    - Distributed rate limiting (multi-instance)
    - Session store (sticky sessions not needed)
    - Real-time counters (emails sent today per tenant)
    - Message queue (job scheduling)
    - Cache layer for expensive queries

Implementation:
  1. Deploy Redis (AWS ElastiCache or self-hosted)
  2. Add Redis client to engine
  3. Implement rate limiter using Redis INCR
  4. Implement session store (JWT in Redis)
  5. Cache expensive DB queries (24h TTL)
  6. Implement message queue for background jobs

Example Rate Limiter:
  async function rateLimit(tenant_id, limit = 40, window = 86400) {
    const key = `rate_limit:email:${tenant_id}:${today}`;
    const count = await redis.incr(key);
    if (count === 1) await redis.expire(key, window);
    return count <= limit;
  }

Success Criteria:
  ✅ Rate limiting works across all instances
  ✅ Multi-instance deployment without sticky sessions
  ✅ Response times improved (query cache)
  ✅ Database load reduced by 40%

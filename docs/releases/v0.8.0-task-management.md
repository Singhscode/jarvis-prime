# Version 0.8.0 — Task Management

## Summary
Phase 5 completes the implemented customer-lifecycle workflow: Website Lead → CRM Lead → Client → Project → Task. It adds the smallest useful task-management surface within the existing CRM module.

## Added
- Project-nested task creation, listing, update, completion/reopening, and deletion.
- Required Project → Task relationship and a minimal five-column `crm_tasks` table.
- Owner-scoped task access and project deletion protection while tasks exist.

## Improved
Projects now model their actionable work with the minimal `completed` lifecycle state, without introducing a status system or workflow framework.

## Database Changes
Migration `20260715000007_create_crm_tasks.sql` adds `crm_tasks`, a `project_id` index, a restrictive project foreign key, and RLS enablement. The canonical migration must be applied through the separately approved database process.

## API Changes
Added `GET` and `POST /api/projects/:projectId/tasks`, plus `PATCH` and `DELETE /api/projects/:projectId/tasks/:taskId`. There is no standalone or versioned task endpoint, global task list, detail endpoint, bulk API, or reassignment API.

## Security
All task endpoints use existing JWT authentication. Every operation verifies parent-project ownership and scopes task access by `owner_user_id` and `project_id`. The migration enables RLS; current API isolation is enforced by the owner-scoped application queries using the configured service-role client.

## Tests
The existing release checks pass: API tests 41/41, ICP scorer tests 16/16, root lint, root build, diagnostics, and diff checks. Task-specific automated and live database integration tests have not been added.

## Architecture Decisions
Task Management extends the existing CRM module only. It adds no separate Tasks module, generic CRUD, generic repository, generic service, duplicate middleware, or unnecessary abstraction. The REST API remains nested beneath projects and the schema contains only current runtime fields.

## Technical Debt
No new architectural debt was introduced. Independent database RLS policies and task-specific integration coverage remain deliberate follow-up work when needed by a confirmed runtime requirement.

## Known Limitations
Tasks have no global list, direct lead/client/contact/company relationship, assignment, dates, description, priority, labels, ordering, comments, subtasks, attachments, time tracking, history, automation, or single-task read endpoint. Duplicate names are allowed and task-list order is unspecified.

## Upgrade Notes
Apply the canonical migration through the approved database process. Do not run a local database reset against data that must be preserved. No local Docker or Supabase data operation is part of this release preparation.
